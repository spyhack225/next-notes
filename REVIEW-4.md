## Remaining finding

**MEDIUM — The service epoch tracks entry to service methods, not every grant withdrawal/replacement.** `Sources/NextNotes/Calendar/CalendarService.swift:227`, `:242`, `:259`, `:273`; upstream transition at `Sources/NextNotes/Calendar/Google/GoogleOAuthClient.swift:104`, and controller ordering at `Sources/NextNotes/Calendar/Google/GoogleConnection.swift:207`, `:210`, `:211`, `:218`.

Failing situation through the controller: start a Calendar list read under A and hold its successful HTTP response after token/backing admission. Connect B with Docs-only scopes. OAuth saves B at `GoogleOAuthClient.swift:104` before returning. `GoogleConnection.connect()` then awaits the managed tool installer at `:210`, before invoking the Calendar callback at `:211`. Release A's response while installation is suspended: no service epoch has changed, so `CalendarService.swift:273` accepts A's list under B. If installation throws, the catch only sets connection state; the Calendar callback never runs and no later epoch bump/clear is guaranteed. The same missing fence affects Calendar-to-Calendar replacement. The live installer can fail or cancel (`ManagedWorkspaceTool.swift:129`, `:149`, `:151`, `:153`). This is an actual in-process replacement, independent of external Keychain writers.

A second ordering still restores entries **after a clear** through the direct service route. Begin `CalendarService.connectGoogle()`, which increments the epoch at `:227`, then waits for browser sign-in at `:234`. While that await is pending and A is still saved, the Settings list caller (`CalendarSettingsTab.swift:32`) starts a list read, increments/captures a newer epoch and reaches A's HTTP backing. Hold that response. Finish sign-in with Docs-only B: the `.disabled` branch clears the list at `:242` and awaits event refresh, but never advances the epoch again. Release A's held response after connect returns. Its newer captured epoch still matches, so it restores A's list at `:274`. MainActor isolation permits this ordering across the sign-in await; the provider is likewise reentrant while authorizing.

The grant producer also clears on `invalid_grant` without touching this epoch (`GoogleAccessTokens.swift:110`, `:112`). An independently admitted old successful HTTP response can therefore publish after that withdrawal unless another list/service transition happens. Successful controller disconnect does eventually invalidate at its list callback (`GoogleConnection.swift:135`, `:136`), but clearing/replacing the stored grant itself has no service epoch notification.

Required repair: fence list publication against the actual grant identity/transition through the existing producer/service seam, including controller installation failure and list admission during sign-in. Add held-response coverage for those orderings. A bump only before a long sign-in await, or only after tool preparation succeeds, does not establish the requested every-path contract. These are static failing interleavings, not new native reproductions.
