## Remaining findings

1. **MEDIUM — A replaced grant can still deliver/launch with its old successful token.** `Sources/NextNotes/Calendar/Google/GoogleAccessTokens.swift:71`, `:104`, `Sources/NextNotes/Agent/GoogleWorkspaceCLI.swift:497`, `:513`. The identity/generation guard exists inside the refresh task before it completes. After awaiting its value, both creator and joining waiters check only caller cancellation. A refresh can complete for grant A, then `replaceGrant(B)` can run before a suspended waiter resumes. Cancelling an already completed refresh cannot change its successful value, so that waiter returns A. Separately, the runner may already have received A when B replaces it: at executable admission it checks cancellation but never compares its saved grant identity again. A send admitted under A's scopes can consequently launch with A after reconnect to B, or can check A's scopes and acquire B's token if replacement wins the earlier actor hop. Bind scope admission/token delivery to the same grant identity and refuse changed-grant launch. Add held successful-refresh/reconnect and after-token replacement cases, using the existing gates. This is a static interleaving, not a native reproduction; the added R3 tests hold invalid_grant responses, and the after-token fixture injects cancellation only.

2. **MEDIUM — Connection-controller withdrawal retains old Calendar list data.** `Sources/NextNotes/Calendar/Google/GoogleConnection.swift:149`, `:161`, `Sources/NextNotes/Calendar/CalendarService.swift:252`. Start with `CalendarService.shared.googleCalendars` populated, then reconnect through `GoogleConnection` with a Docs-only grant. `applyCalendarGrant` switches `calendarGoogleEnabled` to false and skips `refreshGoogleCalendars`. `refreshEverythingThatReadsGoogle` now calls only `refresh()`, which replaces upcoming events/provider states but never assigns `googleCalendars`. Even disconnect's new list refresh returns at the enabled guard when Calendar is already off. The old calendar IDs/names remain cached indefinitely on this route. Clear that list through the existing service seam on withdrawal/disconnect regardless of the enabled switch, without entering Google backing. The new withdrawal fixture covers `CalendarService.connectGoogle`, not this connection-controller flow; its success does not cover this defect. Static path inspection, not executed here.
