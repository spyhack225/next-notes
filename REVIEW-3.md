## Remaining finding

**MEDIUM — An outstanding Calendar list response can repopulate the cache after controller withdrawal or disconnect.** `Sources/NextNotes/Calendar/CalendarService.swift:253`, `:262`; controller callers at `Sources/NextNotes/Calendar/Google/GoogleConnection.swift:125`, `:136`.

Failing situation: with Calendar enabled under grant A, start `refreshGoogleCalendars()` and hold a successful A calendarList response after the HTTP request has entered backing. While the service is suspended at `:262`, reconnect through the controller with a Docs-only grant B. The repaired callback switches Calendar off and clears `googleCalendars` at `:254`; controller refresh can then finish. Release the older successful response. The first service invocation resumes and unconditionally assigns A's list at `:262`, restoring the withdrawn account's IDs/names while Calendar is off. The same ordering works across disconnect, including a response for an already processed request arriving after revocation/clearing. `refresh()` updates events and provider states, not `googleCalendars`, so subsequent ordinary polling does not remove the restored list.

This is a static interleaving, not a native reproduction. MainActor isolation does not prevent reentrancy across the awaited list request. There is a normal independent list caller in `Sources/NextNotes/UI/Settings/CalendarSettingsTab.swift:32`. The provider admits authorization before the request (`GoogleCalendarProvider.swift:103`) and decodes successful responses without a post-response grant check (`:264`). The new token-delivery checks do not fence a Calendar HTTP request that already received its token and entered backing.

The new controller fixtures populate and fully await the list before withdrawing (`GoogleCalendarWithdrawalSelfTest.swift:42`, `:62`) and before disconnecting (`:70`, `:73`); they never hold an old list response across the clear. This is an unfixed edge of the repaired cache contract, not evidence that the repair introduces a new API call. Fence list publication against withdrawal/disconnect and exact grant replacement, using the existing service/provider seam, and add a held successful-list-response case. Simply checking the enabled switch would miss an A-to-B replacement where both grants permit Calendar.

## Admission, locking and legitimate reconnect checks

- **Last identity check to `process.run()`:** there is an instruction-level interval between `GoogleTokenStore.swift:110` and `GoogleWorkspaceCLI.swift:711`, including entry to `ProcessBox.launch`, acquisition of its lock, and cancellation checks. There is no suspension and no in-process grant-replacement window: `withMatchingGrant` holds the same recursive token-store lock used by save/clear throughout its synchronous body. A replacement that wins first causes refusal; one arriving after successful launch admission waits until `process.run()` returns. This is an acceptable launch boundary. A process already admitted can continue using A after a later reconnect; this repair does not cancel an already launched operation. Another process writing Keychain is outside this in-process lock's protection.
- **Deadlocks:** recursive acquisition by `savedGrant()` under `withMatchingGrant` is intentional (`GoogleTokenStore.swift:15`, `:31`, `:109`). The new nesting is token-store lock then ProcessBox lock. Cancellation/resume/timeout handlers acquire only ProcessBox's lock and never the token-store lock, and the termination handler schedules result work rather than awaiting token-actor work. Replacement saves synchronously then invalidates on its actor (`GoogleAccessTokens.swift:131`). No actor await occurs under the token-store lock and no reverse lock acquisition was found. Failure unwinds both locks before closing pipe writers/resuming at `GoogleWorkspaceCLI.swift:639`. Actual Foundation/Keychain blocking behavior was not exercised.
- **Legitimate re-grant:** save gives every record a fresh UUID (`GoogleTokenStore.swift:70`), even for the same refresh-token text. Old admitted calls refuse; a fresh call captures the replacement identity/scopes, obtains its new cache/refresh result, and passes the final matching-record fence. A direct-store replacement also stops using cached A because cache identity includes the record bytes (`GoogleAccessTokens.swift:78`, `:79`). A newly expanded grant can therefore run the newly permitted command. The retained positive executable case after re-grant is `GoogleGrantLaunchSelfTest.swift:49`; same-text fresh-call success is supported by static tracing, not a dedicated positive fixture here.
- **Plain changed-sign-in state:** `GoogleCalendarProvider.swift:346` defines “Your Google sign-in changed, try again.” `GoogleConnection.swift:80` preserves it when it is the state's raw failure reason. Token-admission rejection maps to a known pre-launch `WorkspaceCLIError.launchFailed` at `GoogleWorkspaceCLI.swift:505`; final launch refusal maps through `:643`. That command error adds the existing plain “Next Notes couldn’t reach Google:” prefix. `GoogleGrantLaunchSelfTest.swift:12` checks raw state detail and `:41` checks typed, known-outcome refusal at all three seams. Visible UI transitions were not exercised.
- **Calendar clearing:** disabled entry clears before entering the provider at all. Enabled-but-unauthorized entry reads local configuration/grant state and clears before token/network backing. Live disconnect separately attempts Google revocation at `GoogleConnection.swift:134`; the zero-backing claim applies to cache clearing, not to that intentional revocation or all subsequent workspace-status work. No switch value fixes the outstanding-response publication race above.
