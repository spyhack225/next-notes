  (`Agent/Tasks/AgentTaskManager.swift:19-28`) fails every running task at each `make install`,

### 0.2 Why the split does not create a second ledger

Most of this phase already sits **under** the ledger Phase 3 will build, not beside it:

- `TaskID.raw` **is** `AgentTask.id` (P3 §2.1), and P3 §2.5's table maps every `TaskState` onto the
  **persisted** `AgentTaskStatus` (`Agent/Tasks/AgentTask.swift:3-12`). `TaskBridge` stores its
  tasks as `AgentTask` rows.
- P6-02's store replaces `agent-tasks.json`, which `AgentTaskManager` owns today. P6-04 already
  names `AgentTask`'s hand-written `init(from:)` as where the durability fields decode, and
  `AgentTaskManager.init` as the switch point.

So making `AgentTaskManager`'s store durable first **upgrades the one ledger that exists**. When
`TaskBridge` arrives it wraps a store that already survives a restart. The AGENTS.md rule — one
task ledger, one channel that starts audio, one tool manifest, one usage log — is kept: nothing in
6A is a second anything.

## 1. Phase overview

### 1.1 Goal

Background work survives the process. A task that was `running`, `queued`, `needsInput` or
`needsPermission` when Next Notes quit is **recovered, resumed or reported** at the next launch,
and a task is never marked failed merely because the app was closed.

The exit is one sentence a user could read and believe: *"I asked it to do three things, I quit
the app, and when I came back it had finished two and told me the third needed me."*

### 1.2 What is missing today (D1–D8)

| ID | Defect | Anchor |
|---|---|---|
| **D1** | **The entire restart path is four lines.** `AgentTaskManager.init` maps `running` and `queued` to `.failed` with the message "Next Notes quit while this task was running." There is no re-queue, no resume, no checkpoint. | `Agent/Tasks/AgentTaskManager.swift:19-28` |
| **D2** | In-flight work state is in memory only: `running: [String: Task<Void, Never>]`, `approvedTaskIDs`, `approvedCompatibilityTaskIDs`. An approval granted before a quit is forgotten, so the task fails on relaunch even though the person already said yes. | `AgentTaskManager.swift:11-17` (all `@ObservationIgnored`) |
| **D3** | The store is a whole-file JSON rewrite: `save(_:)` re-encodes every task and writes atomically, on every change. It is history, not a record — its own header says "they are not durable workflows". | `Agent/Tasks/AgentTaskStore.swift:3-4, 22-28` |
| **D4** | There is no event log. `AgentActivityStore` keeps 80 in-memory activities and a capped 400-row `agent-audit.jsonl`; neither records a state transition in a form recovery could replay. | `Agent/Activity/AgentActivityStore.swift:36` |
| **D5** | There is no heartbeat, so "still working" and "wedged" are indistinguishable. | absent |
| **D6** | There is no retry policy. A failed tool turn ends the task; nothing is retried and nothing records that it could have been. | absent |
| **D7** | `AgentArtifactLedger` is in-memory only — `nonisolated(unsafe) static var byTask` behind an `NSLock`. A restart loses every artifact a completed task produced. | `Agent/Tasks/AgentArtifactLedger.swift:16` |

### 1.5 Prior art: OpenMuse's task worker (added 2026-09-27)

CopilotKit's OpenMuse (`github.com/copilotkit/openmuse`, MIT, read at `34b15bc`) ships the thing this
phase plans: durable jobs on PGlite/PostgreSQL with pause, resume, cancel, retry and recovery of
interrupted work. `apps/server/src/engine/worker.ts` is about 200 lines and worth reading before
P6-04a/P6-05. Three of its choices are adopted as amendments (`REVIEW-LOG.md` §7, O3–O4); two are not.

| OpenMuse does | Here |
|---|---|
| Every checkpoint is a compare-and-set on `{leaseId, status: "running"}`; a write from an executor that lost its lease is dropped | **Adopted** as P6-06 step 5, keyed on `attempt` rather than a lease id: a result, event or effect from a superseded attempt is refused in the same transaction |
| "No hidden retry after an uncertain external write. Review its provider outcome before creating a replacement." | **Adopted** as P6-06 step 6, with one improvement it does not have: where a read can answer "did it happen?" (a sent message, a created event), the app reads it back before asking the person |
| A two-worker lease race and an expired-lease recovery are tested against a real restart | **Adopted** as the shape of `--selftest-task-recovery`'s crash cases (P6-04a): a real reopen of the store, not a mocked one |
| The lease is renewed on a timer at a third of its length | **Not adopted.** §2.5's beats are event-driven, and only `acpWorker` and `scheduledResearch` get a periodic beat; a timer per task is the cost §2.5 exists to avoid |
| Two processes coordinate through the lease | **Not adopted.** One app process owns the ledger; `leaseOwner` is a pid (§2.2) and the orphan reaper (P6-04a step 5) is the whole cross-process story |

## 2. Contracts

### 2.1 The extension point

**Under 6A (adopted 2026-09-27) the fields live on `AgentTask` first**, because 6A lands before
`TaskRecord` exists: `TaskDurability` is an optional field of `AgentTask`, decoded in its
hand-written `init(from:)` (`Agent/Tasks/AgentTask.swift:115`), and `.recovering` is an
`AgentTaskStatus` case. When P3-03a builds `TaskRecord` over `AgentTask` rows it reads the same field,
and P6-04b adds the `TaskState` case. Nothing is stored twice.

`TaskRecord` (`04-PHASE-3-FULL-DUPLEX.md` §2.5) gains these fields. Every one is **optional with a
default** in the `Codable` conformance, and `TaskState` gains exactly one case.

```swift
// Added to TaskState (§2.5's table), and to its `legal` map only as a recovery entry point:
case recovering
//   .recovering is reachable ONLY from .running and .delegated, and only from the recovery
//   planner at launch. Every other transition out of it is .running, .failed or .cancelled.
//   A live task must never enter .recovering while the process is up.

struct TaskDurability: Codable, Sendable, Equatable {

    var attempt: Int                    // 0 until the first worker start
    var retryCount: Int
    var maxRetries: Int
    var lastProgressAt: Date?
    var resumePolicy: TaskResumePolicy  // .retry, .resumeFromCheckpoint, .verifyThenDecide, .neverAuto
    var leaseOwner: String?             // the pid that owns the run; reaped on launch (P6-04a)
    var runtimeClass: TaskRuntimeClass  // drives the stale window (P6-05)
    var receiptIDs: [String]            // ActionReceipt ids this task produced (P6-06)
    var parentTaskID: TaskID?           // fan-out (P6-10)
    var attemptStartedAt: Date?
    var terminalReason: String?         // why recovery decided what it decided
}
```

```swift
enum TaskResumePolicy: String, Codable, Sendable {
    case retry                      // pure work: search, read, model completion, indexing
    case resumeFromCheckpoint       // a backend that can be reconnected (ACP)
    case verifyThenDecide           // anything that may have mutated something
    case neverAuto                  // a person must be asked; restore a card
}

enum TaskRuntimeClass: String, Codable, Sendable {
    case localDeterministic   // stale after 30 s
    case cloudModel           // 5 min
    case browserOrMCP         // 5 min
    case acpWorker            // 15 min
    case scheduledResearch    // 30 min
    case waitingOnPerson      // no stale window at all — see §2.5
}
```

`TaskRecord` is `Codable` with a **hand-written** conformance? No — it is synthesized today. The
rule that applies is the `Meeting` rule: **the durability fields are added with a hand-written
`init(from:)` using `decodeIfPresent` for every new field**, or a `TaskRecord` written by an older
build (or a seeded fixture, or a ledger row imported from `agent-tasks.json`) fails to decode and
the task vanishes. This is the same trap as `MeetingModels.swift` and it is the single most
likely way this phase ships broken.

`AgentTask` (`Agent/Tasks/AgentTask.swift:33`) already has a hand-written `init(from:)` at :115
doing exactly this for its own fields. Reuse the pattern; do not add a second `AgentTask`.

#### 2.2.1 Artifacts and evidence are different things (added 2026-09-27)

OpenMuse keeps three records apart: **evidence** (what the agent read — mail, a file, a page, the
person's words), **artifacts** (what it produced — a document, an event, a report), and
**receipts** (what an action did). This app has all three, but only receipts are typed:
`AgentArtifactLedger` holds bare strings (D7), and `ActionContextReference`
(`Agent/ActionRuntime.swift:83`) is an untyped `{kind, value}`. The rules this phase adopts:

1. **An artifact row has a kind and a plain title** (the two columns above), filled from
   `AgentToolResult.reference`/`link` and the tool that produced it. That is what lets a finished
   task say "Made: *Trip plan* (document), *Dinner with Ana* (event)", not a list of ids.
2. **Evidence is a reference, never a copy.** `ActionContextReference` gains optional `title`
   and `at`, plus a `source` of mail, calendar, file, web, meeting or person. A mail reference
   holds the message id and a title such as "Ana, Tue 14:02", not the body. This keeps §2.2's
   rule that no task row stores message text, and it keeps evidence out of `usage.jsonl`.
3. **Evidence never becomes authority.** That already holds — `ActionIntent.authority` is set by
   who asked, not by what was read — and this phase must not weaken it. A self-test pins it (P6-02
   step 7).
4. **Where it shows:** the approval card and the result each carry one "Based on" line built from
   the evidence titles, so a person can see why the agent thinks what it thinks without reading a
   transcript. The line goes through `AgentActivityProjector`'s public-title rule.

### 2.3 The event journal

`TaskEvent` (§2.5) becomes both a stream and a record. The `AsyncStream` contract does not change;
what is new is that **each event is written to `task_event` in the same transaction as the state
change it describes**, and the journal is the recovery input.

```swift
enum TaskEventKind: String, Codable, Sendable {
    case jobCreated, workerStarted, toolStarted, toolCompleted
    case permissionRequested, permissionApproved, permissionDenied
    case artifactCaptured, heartbeat, retryScheduled, workerRecovered
    case jobCompleted, jobFailed, jobCancelled
    case revisionRecorded, dependencySatisfied
    case staleAttemptDropped, outcomeResolved   // P6-06 steps 5–6 (OpenMuse 2026-09-27)
}
```

Two rules that are the difference between a journal and a log:

- **Atomicity.** A state change with no journal row is a bug, and P6-03's self-test fails on it by
  killing a seeded write between the two. `TaskStore.transaction` exists for this.
- **Bounded, and bounded on purpose.** `task_event` grows for the life of a task. Retention is
  30 days for terminal tasks and **forever for a task with a `receiptIDs` entry** — a consequential
  action's history is exactly what a person needs to audit later, so it is not swept with the
  debug rows. State the number; do not leave it implicit.

### 2.4 The recovery planner — a pure table

`TaskRecoveryPlanner.plan(_:) -> TaskRecoveryPlan` is **pure**. No I/O, no clock, no model. It is
modelled on `MeetingStore.resumeAction` (:187), which is pure and is why
`--selftest-meeting-resume` can grade 14 rows instantly.

```swift
enum TaskRecoveryAction: Sendable, Equatable {
    case resumeCheckpoint            // reattach to a live backend session
    case retryAttempt                // safe: pre-mutation, idempotent
    case verifyThenDecide(receiptIDs: [String])
    case restoreCard(reason: String) // needsInput / needsPermission → put the card back
    case reportFailed(reason: String)
}

struct TaskRecoveryPlan: Sendable, Equatable {
    let action: TaskRecoveryAction
    let reason: String               // one plain sentence, shown in the Activity feed
}
```

The table. **This is the whole point of the phase** — the last column is the reason:

| On disk | `resumePolicy` | Action | Why |
|---|---|---|---|
| `queued` | any | `retryAttempt` | never started; nothing happened |
| `running`, `localDeterministic` | `.retry` | `retryAttempt` | a read, a search, an index pass |
| `running`, `cloudModel` | `.retry` | `retryAttempt` | a model completion is not a side effect |
| `running`, `browserOrMCP` | `.retry` | `retryAttempt` | navigation and read; re-navigate is safe |
| `running`, `acpWorker` | `.resumeFromCheckpoint` | `resumeCheckpoint` | reconnect if the child pid is alive, else `retryAttempt` **only if no tool was in flight** |
| `running`, any | `.verifyThenDecide` | `verifyThenDecide(receiptIDs:)` | **never blind-retry a consequential action** |
| `running`, any, with a file mutation in scope | `.verifyThenDecide` | `verifyThenDecide` | see §2.4.1 |
| `running`, no heartbeat within its class window (§2.5) | any | `verifyThenDecide` | a silent job is not a healthy job |
| `needsInput` | any | `restoreCard` | the question is still the question |
| `needsPermission` | any | `restoreCard` | the approval is still pending — including one granted before the quit (D2) |
| `cancelling` | any | `resumeCheckpoint` or `reportFailed` | decide from the backend, not from the flag |
| `completed` / `failed` / `cancelled` | any | **no action** | terminal; the ledger is history |

#### 2.4.1 The file-mutation question, answered here

`action-receipts.json` records `PreparedAction`s that went through `ActionOrchestrator`. A worker
writing a scratch file through a scoped path may not have one. Leaving this undefined is how a
retry duplicates a side effect, so **P6-06 decides it**: a scoped file mutation **must** produce an
`ActionReceipt` at the `verifying` stage, or the journal must record a `toolCompleted` event with
the resulting path so recovery can check the filesystem. The first is preferred; the second is
acceptable only with a comment naming the gap.

### 2.5 Heartbeat and stale detection

Event-driven beats, never a timer per task:

```text
model token · tool event · ACP event · journal write
        ↓
heartbeatAt = now
```

A periodic beat exists **only** for `acpWorker` and `scheduledResearch`, where the underlying
runtime can be silent for minutes. Every other class is beat by its own activity.

`waitingOnPerson` has **no stale window.** A card the person has not answered is not a wedged job,
and the tempting "fail anything with no heartbeat for 30 minutes" rule would fail every pending
approval overnight.

### 2.6 Retry policy, and the receipt rule

Auto-retry **only** for known-idempotent or pre-mutation work:

| Retry automatically | Never retry blindly |
|---|---|
| search, read, model completion, indexing, page load | email send, message send |
| an ACP handshake that failed before any tool ran | file deletion, purchase, external submission |
| a tool that never reached `fire` | calendar invite, git push, anything in `PermissionPolicy.allowsAutomatically` that is `false` |

For everything in the right column:

```text
recovery → read the task's receiptIDs
         → ask ActionReceiptStore whether the action reached a terminal status
         → if it did: do not fire again; continue or report
         → if it did not: a person decides, or a re-prepare is offered
```

`AgentRisk` (`Agent/AgentModels.swift:10`) is the idempotence input: anything `.write`, `.send`,
`.purchase`, `.destructive` or `.privileged` is in the right column, and
`PermissionPolicy.allowsAutomatically` (`Agent/Permissions/PermissionPolicy.swift:114`) is already
`false` for all of them.

Retries are recorded as **attempts** (`attempt`, `retryCount`), and a retry gets a fresh
`attemptStartedAt` so §2.5's window measures the new attempt.

**(OpenMuse 2026-09-27) A superseded attempt cannot write.** A retry starts attempt N+1 while
attempt N's Swift `Task` may not have observed its cancellation yet. Every state change, journal
event, result and effect carries the attempt that produced it, and the store refuses one whose
attempt is not the task's current attempt, in the same transaction (`staleAttemptDropped` is
journalled). Without it a late completion from attempt N overwrites attempt N+1's state — the
failure OpenMuse's lease-id compare-and-set exists to prevent.

**(OpenMuse 2026-09-27) "Fired, no terminal status" is its own answer.** A receipt that reached
`.fired` and never `.completed`/`.failed` (`ActionReceiptStatus`, `Agent/ActionRuntime.swift:255`)
means the outcome is unknown, which is different from "never fired". Recovery first tries to
answer it with a **read** — the sent message in the Sent folder, the created event on the calendar,
the appended text in the document — through the same `verifyResult` path
(`Agent/ActionRuntime.swift:638`). Found → record `completed` and continue. Not found, or no read
can tell → the person is asked, in words: "I'm not sure the email to Ana went out. It isn't in your
Sent folder yet — send it again?" A re-send is a new approval; it is never automatic.

### 2.7 Usage is a projection, never a second log

`UsageRecord` (`Support/Usage/UsageRecord.swift:11`) gains an optional `taskID`. A job's token and
cost numbers are the sum of the rows carrying that id — computed on read, not stored twice.

- **No `AgentUsageLedger` type and no `job_usage` table.** The absorbed roadmap proposed both; the
  absorbed proposal is rejected (P0-20a already built the log, its rotation, its
  `sanitise`, and its harness isolation).
- **Every field passes through `UsageLog.sanitise` exactly as a dictation row does.** A job
  objective, a tool argument or a file name must never reach `usage.jsonl`.
- **Cost stays `nil`.** `UsageLog` records tokens and model identity and prices nothing. Do not
  invent a price table inside a task store; populate cost when `UsageSummary` can source it.
- P6-20d's `--usage-report` is the reader. A job detail is a filter, not a new tool.

### 2.8 Job dependencies (P6-10)
