# Whole-meeting experience: preparation, review and reliable updates

Design-only source audit, 13 October 2026. No production code, UI, inference, compiler or tests were changed/run by this review. All proposed behavior and acceptance remain unimplemented/unverified. Root owns roadmap ordering and signed baseline execution. This plan reuses the private three-meeting audit, including 27 selected material omissions; named cases and speech remain private. [Current redacted notes audit](../../2026-10-13-audit/notes/NOTES-VS-TRANSCRIPTS.md) is the evidence boundary, not an audio accuracy score.

The intended experience is straightforward: Next Notes prepares useful context before a scheduled conversation, records under existing permission and recording choices, explains what is happening, and asks a small number of meaningful questions afterward. Saving an answer updates the meeting and refreshes derived notes in the background. Uncertainty, source loss and old notes remain visible. Confirming a speaker or a note never sends a message or authorizes another external action.

## 2. Before the meeting: prepare without making setup a job

Use the existing calendar occurrence and lead window. Show a compact, immediately available card: meeting title/time, people on the invite, purpose from the invitation, and two or three useful referenced prior facts/open threads. Prior context is labeled as prior context; uncertain or outdated questions are not described as current agreed plans. A suggested objective/question is preparation, not a statement of what the meeting will decide. A document appears only when an already-authorized local index or connected source supplies it.

The first useful version does not require a model: existing bounded retrieval can render source excerpts/links. If an existing meetingStarting routine is available and needed, its current runner/context/permission rules prepare a richer result off the capture path. Do not duplicate it with a second agent or mandatory inference. Relevance and consent must be checked for the actual reader; a brief assembled locally may not be handed blindly to a cloud agent. Missing calendar access gives an ad hoc recording path and one clear grant action if the person requests calendar preparation; missing notifications gives in-app prep, not a broken pipeline.

An upcoming meeting can be canceled, moved, declined, renamed or present in two calendars. Reuse CalendarService identity/dedup and scheduler correlation, retaining provider/occurrence association. Re-read before showing/starting; retire old prep when its event changes. Do not reset skip decisions or arm an already completed meeting to provide a brief. A call detected with no calendar gets its observed app/title and available context; attendees remain unknown. A user-supplied title takes priority over automatic candidates. No microphone/tap permission is inferred from reading a calendar.

## 3. Post-meeting review: one light surface, only useful uncertainty

Reuse the current meeting detail/speaker sheet and notesReady notification/Island event. Present a nonmodal card after capture has stopped and stable issues exist: “A quick check for this meeting.” It opens the same review in the detail view. Do not steal focus during a live call, voice turn or held dictation key. If another call starts, keep the unresolved item in the meeting list/detail; do not interrupt or hold recording. When no meaningful uncertainty exists, a quiet “Notes are ready” is sufficient. The initial end event may show finishing progress before notes exist; it must not announce complete notes prematurely.

Possible rows, generated only from actual evidence:

- **Title:** a placeholder or unresolved detected-call title: choose suggested title, edit, or keep current. A user title is not challenged every meeting.
- **Who said this?** An unknown generated/source label, supported by a short transcript excerpt and an optional already-kept audio clip the person chooses to play. Offer invitation names as suggestions, not inferred assignments; allow Unknown/Not sure. Name-only confirmation updates the existing mapping. Reclustering is a separate explicit action available only with real audio. If the remote track could contain several people, ask that distinction rather than naming the whole track from roster order.
- **What was the follow-up?** Show the complete anchored request/intention, with the uncertain part emphasized: requester/provider, proposed versus accepted, past versus future, date supplied versus absent. Choices can confirm the exact interpretation, change it, or leave uncertain. A user-confirmed correction is labeled as such; it is not fabricated transcript speech.
- **Coverage:** a factual notice when recorded counters/pass rejection show a missing source. Explain whether a saved complete recording can recover it. There is no Confirm button that restores missing audio; the person may add a note or keep reading partial notes.
- **Notes:** only an established mismatch/stale source or a particular unresolved claim needs an answer. Do not ask the user to certify an entire generated document because the model returned valid Markdown. Broad confidence scores are not a reason to hide review.

One “Save changes” applies the local, reversible corrections and immediately acknowledges accepted fields. “Later” or dismissal preserves unresolved status without false confirmation or repeated popups for the same revision. No action is executed by saving a name/title/request correction. External sends/invites/writes remain on the existing exact-payload review/approval card; do not add a second execution approval to this local check, nor reuse local confirmation as an approval token.

Reuse stable notification identifiers and NavigationState.show(meeting:) so notification, Island and meeting detail answer the same item. A stored per-meeting reviewed/dismissed revision becomes justified only for persistent duplicate prevention; use optional metadata in the existing Meeting record, not a new review database/history/queue. Avoid prompting once per individual service callback. New uncertainty caused by a materially changed source can reopen the affected row, with the reason shown; unchanged confirmed rows stay settled. An old delivered notification is navigation, never authority to accept a newer unseen interpretation.

## 4. Revision and update contract

The audit demonstrates the need: saved notes can predate a later transcript/speaker revision, and a failed refresh leaves older content. The correct repair belongs to the writer/save producers, not global replacement of names in Markdown. Free prose is not a safe map of speaker IDs; a blind replace could alter quotations, unrelated names or a newly changed cluster.

Minimum proposed witnesses live beside existing Meeting metadata and generated notes: a digest/version of the actual eligible transcript, source clocks/coverage and accepted speaker mapping used by the writer; the resulting Markdown identity; and local review revision when that product exists. Title/brief/confirmed clarification dependencies belong in that actual input witness when they affect the generation. Compute from already loaded/assembled input, not a second transcript read on a capture callback. Existing notes.json generation still describes Markdown extraction; it cannot serve as the transcript-input witness. Legacy absence means unknown, not matching/current.

At the start of NotesService generation, capture this input witness and the current note identity. After completion, reread the existing row and verify the source version, manual notes and task owner before replacement. Preserve manual scratchpad through the existing merger. If the user externally edited the generated file meanwhile, retain the edit and present the withheld generated result as unavailable/requiring review; do not overwrite it just because the meeting still exists. A deleted meeting cannot be recreated. Markdown writes and metadata writes are separate existing file operations: publish Current only when the accepted output identity and input witness match. A failure/crash between them is stale/unknown, never silently current; no cross-file transaction guarantee is claimed.

After accepted name save, source/title correction, or successful speaker-label commit, update transcript/context immediately and request one background refresh through the same NotesService. Name correction and notes regeneration use saved text: **zero ASR calls**. Successful reclustering uses kept audio for diarization only, then regenerates notes from the saved transcript: no needless final ASR. Expired audio still permits names/text/title clarification and notes generation from saved text, but never a promise to reidentify voices or recover words.

If generation is running when another correction arrives, its captured output must not overwrite the newer source. Keep only the latest requested revision in the existing per-meeting service entry, then run the latest needed refresh when that owner settles. This small coalescing state is justified by the edit-during-generation race; do not add a second job queue or repeated semantic checker. Scratchpad-only edits use the existing idempotent manual-note merge and must not trigger new inference. A no-op name/title save also requires no generation. Each newly accepted material source revision may require one actual new notes generation. A failed unchanged-input attempt does not authorize an automatic retry loop. Automatic refresh must preserve selected model/privacy policy, not switch providers because a cloud request failed.

Confirmed semantic corrections require a distinctly labeled user-confirmation block through NotesPrompts.notesUser/NotesService's existing input seam or existing source-aware context fields; they cannot be smuggled into Known context, whose rules exclude it from current-meeting facts. Preserve quote/source/time and actor identity on requests. This is a future producer-contract change requiring original/fixed proof; merely adding prompt wording is not demonstrated semantic repair. Action drafts affected by changed meaning must become stale/held; committed receipts remain historical facts and must never be replayed automatically. Existing forced Review again replaces offers, but automatic regeneration must not emit duplicate proposals or re-run notesReady routines.

## 5. State/event contract

| Event | Visible state / source of truth | Allowed next work | Required refusal/admission |
|---|---|---|---|
| Calendar occurrence enters lead window | Prepared info derived from event/current authorized sources | Bounded retrieval, optional existing trigger | No record/voice binding or external write implied |
| Record agreement/start | Existing armed→recording; actual capture starts before ASR warm-up | Two-track writer/live ASR | Existing mic/tap/record authority; partial tap refusal visible |
| Stop/call-ended | Saving last words; capture and its drain close | Existing final→diarize→notes handoff | No new recording until actual capture/drain owner releases; heavy postprocessing not part of that gate |
| Saved recording incomplete | Partial transcript / unavailable source | Safe retained live text; supported remaining pipeline | Do not run recovery on incomplete saved audio as though complete; no guessed remote answers |
| Final pass accepted/rejected | Exact transcriptPass/counters | Diarization only when eligible, then notes | Rejection means live kept, not word-accurate verification |
| Stable unknown labels | Review-needed row with excerpt/invite suggestions | Optional user naming; ongoing notes can use neutral labels | Roster/cluster count is not person identity or execution authority |
| Notes complete | Accepted output/source witness + quality/coverage limits | Quiet notice or relevant review; existing extraction/review | Normal stop is not factuality; do not label complete if source lost |
| Local answer saved | Accepted mapping/title/context; updating notes shown | One source-driven background refresh, no ASR | Re-read current row; save failure must not claim accepted update |
| Source changes mid-pass | Old note remains readable and visibly older | Latest revision refresh after prior owner settles | Old callback cannot write/current-label/announce/clear newer owner |
| Cloud unavailable/offline | Previous note/transcript available; work paused/failed truthfully | Later explicit retry or same-authorized local route only if existing policy permits | No silent cloud upload/new provider/empty success |
| Dismiss/Later | Unresolved revision retained in meeting detail/list | Other work proceeds | No invented confirmation, repeat popup or blocked microphone |
| Quit/restart | Existing stage ownership drained/canceled; durable input/output witness retained | Existing repair/resumer plans eligible work | No automatic replay of external effects; missing audio remains unavailable |

A new UI “Needs a quick check” is a projection of existing meeting fields and bounded revision metadata, not another pipeline status that blocks a done meeting. Processing completion, output freshness, source coverage and user confirmations are separate facts.

## 6. Edge cases that must be proved

| Edge / race | Desired behavior and original/fixed acceptance |
|---|---|
| Meeting ends as next call starts | Old finishing/review work stays bound to old ID; new capture starts after actual old seat/drain release, without waiting for notes/review. Tests hold old final/model callbacks while admitting next session. |
| Double Stop / detector reconnect / duplicate calendar | Existing stopInProgress and serialized call changes remain; one recording, one finish, one relevant review per accepted revision. Reconnect policy stays scheduler-owned. |
| Two notices or two windows answer | Notification/Island/detail revalidate same current revision; first accepted answer wins; second stale answer cannot replace it. No name-based global UI cleanup. |
| User edits title/names while pass held | Accepted user value persists; old output refused/current row reread; latest-only refresh, no stale title resurrection. |
| User deletes meeting / externally edits note | No recreated directory, false save success, unasked overwrite, extraction or proposal from deleted/stale source. |
| Reclustering reuses Speaker1 string | Retain a prior user mapping only with stable source/interval voice correspondence; surviving string alone is insufficient. Ambiguity becomes a naming check, not confident carryover. Native recluster identity remains an explicit test gap. |
| Remote-only/mic-only/no speech | Truthful missing-side/empty-speech presentation; no invented meeting overview, attendee, unresolved question or follow-up from noise. |
| Legacy counters missing | Unknown coverage; do not turn absence of optional fields into a full-recording badge or reclassify an old owner report as false. |
| Audio expired or unreadable | Notes/names may update from text; no audio replay/diarization/recovery promise. A disk error while saved audio exists differs from expiration; retain source and offer truthful error. |
| Cloud reasoning-only/length/retry | Existing budget/cut disclosure preserved; actual failed output never replaces good older notes or triggers empty-success notices. No additional checker pass. |
| Local answer saved but context/notes save fails | Keep accepted fields and prior outputs, retain partial-save message and needed audio; no success dismissal. Use existing speaker-save contract. |
| Quit mid-refresh / restart after completed metadata | Existing repair reconstructs stale/needed work from same Meeting witnesses, honors user dismissal, does not regenerate matching notes or repeat reviewed external actions. |
| Permission revocation / notification denial / focus mode | Keep local core usable, clear single grant action where necessary, fall back to in-app indicator. No repeated prompts or automatic new cloud consent. |
| Review opened during dictation/voice | No focus steal/audio-preview autoplay; live Island priority preserved. Saving a correction does not hold the mic/model/speaker path. |

## 7. Progress, latency and performance acceptance

Show actual work: Preparing the meeting; Recording; Saving the last words; Checking the recording; Sorting speakers; Writing notes; Updating names/notes; Update failed—previous notes kept. Known fractions come from map count/diarizer progress. Single-pass generation has no reliable percent; show stage and elapsed time, keep previous text readable, and use a provider stream only if that existing API actually supplies it. Do not fake percent/ETA, add a preview generation or rename an indefinite spinner and claim progress solved. Stalls follow existing StageWatch/owned cancellation; a newer revision must not be cleared by an older timeout.

A local confirmation should acknowledge promptly and dismiss without waiting for ASR/notes. Proposed target: visible accepted-change/progress feedback within 100ms p95 on the reference Mac, tested through actual save/UI entry; this is a target, not a measured result. Avoid extra sequential await, sleep/debounce or confirmation on capture/voice paths. Use current service tasks, compute priorities/checkpoints and trigger events for background work. Heavy refresh/prep yields to ASR/voice; no speculative notes model is loaded at record start. Record notes input assembly, lane wait/prefill/generation/save and confirmation-to-visible/current-note times from existing traces/UsageLog; keep content out of aggregate logs. Cloud recorded latency is not local 20 tok/s/reference-workload proof.

Native acceptance includes a visible scheduled/ad hoc recording, back-to-back calls, voice/dictation during refresh, long partial/full-source workloads, stop/restart and foreground responsiveness on 16 GB/256GB M2–M3. Neither a model-free helper pass nor one final transcript establishes this. Do not promote no-WMO diagnostic build performance, a new model or experimental audio/pause defaults from UI scaffolding.

## 9. Privacy, authority and proof gaps

Preparation reads only already-authorized calendar/index/memory sources. Meeting material and calendar text are data, never tool instructions. Actual local/cloud reader decides graph/file consent; no cross-provider cached brief reuse without revalidation. Show one plain opt-in when a person chooses a capability needing a new account/grant; no terminal/API-key/provider-ID requirement in the normal review. Notification text should be minimal and respect existing OS visibility controls; no transcript excerpt, sensitive attendee list or request content on a lock-screen banner by default. Local review can reveal private excerpts inside the meeting view.

Speaker mapping is user-confirmed display attribution or provider/source-linked evidence, not roster guess. Request clarification is evidence about intent, not permission for external writes. Keep the existing durable action/receipt and PermissionGate contracts; no new standing grant, side queue or action ledger. Aggregate performance logs use counts/timing/IDs, and private semantic payloads stay outside Git/relay. The current NotesService logging includes public meeting-title interpolation; any additional semantic trace must use the established private test writer, never mirror owner text into public logs.

Current gaps remain: audio-independent word truth for the three audit meetings; accurate source clocks and recoverability; real participant-to-voice binding; complete semantic notes/action recall; physical speaker-review/menu interactions; automatic prep/review not currently implemented; older notes source witnesses missing; exact original/fixed current writer native comparison; reference-machine long full-duplex throughput and memory; inherited aggregate/browser/voice failures. Saving a local check, passing baseline flags or finishing processing does not close these. This document is the requested before-implementation plan, not a readiness/installation claim.
