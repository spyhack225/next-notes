# Participant information and voice binding: provider acceptance plan

Reviewed 2026-10-08 against current primary provider documentation and existing Next Notes sources. This is a capability/implementation plan, not an implemented provider naming feature. No provider account call, grant request, browser/app launch, compiler or model run was made. Sources/Resources remained frozen for the coordinated sixth native build. Public evidence contains no owner names, email addresses, meeting identifiers or utterances.

Names are obtainable on some routes. Correct automatic attribution requires evidence connecting a participant to the captured speech. A calendar invitation or participant list supplies name candidates; neither supplies that connection. Email is optional and often unavailable. A shared room/device account identifies the endpoint, not every person speaking into it.

## Existing contracts, checked in source

- `CalendarProvider.MeetingEvent.attendees` means invitees other than the user. Google Calendar preserves displayName or falls back to supplied email through `GoogleAttendee.name`; when a displayName exists, its separate email is lost in the current `[String]` projection. EventKit likewise prefers participant name, falling back to its supplied mail address. Neither proves attendance.
- `MeetingScheduler` already correlates detected calls with calendar events. `Meeting` already retains invitation strings, conference URL, provider/event identity and coveringCallID. Detected calls without a calendar match have no implied participant information. No new scheduler or identity store is needed.
- `SpeakerNamesSheet` already presents invitation suggestions as “On the invite.” `Meeting.speakerNames` is the existing label-to-name seam. Confirmed names must survive provider uncertainty and finalization; they must not be replaced by roster order or previous-call guesses.
- `MeetingSpeakerProjection` carries supported existing names/labels into context using source, quote and time evidence; it discovers no people. Its final-label/native51 proof and the participant diagnostic/native19 proof are narrower than live provider identity. The sixth candidate's new rename-save admission/original comparison is pending and owned by root.
- The one-shot Zoom AX/Meet CDP diagnostic has no actual retained participant observation to parse. Its typed names remain empty and active speaker absent. Native19 verifies selection/refusal/privacy contracts only. AX deadline and full CDP reply limits remain open, so it is not a production polling observer.
- Live transcript offsets use the actual recording host clock. Legacy Meeting.start persistence keeps whole ISO seconds; newer performance summaries preserve the recording Date precisely. Neither makes UI arrival time or a provider server timestamp sample-accurate. Cross-clock alignment needs a real producer fixture.

### Zoom

The past-participant endpoint requires a paid Pro-or-higher account and suitable user/admin scope. It returns meeting-instance participant/join information; repeat occurrences need the correct UUID. External email may be blank under Zoom's disclosure rules. These fields cannot identify which local diarized cluster spoke. [Meetings API](https://developers.zoom.us/docs/api/meetings/#operation/pastMeetingParticipants), [email rules](https://developers.zoom.us/docs/api/using-zoom-apis/#email-address-display-rules).

The Apps SDK runs in the Zoom client's embedded app browser. `getMeetingParticipants` and `onActiveSpeakerChange` are Host/Co-Host only, with no Guest Mode. Breakout roster queries concern the current room; participant UUIDs may change on role transitions. The email APIs support additional roles but explicitly ask for consent and return individual responses. Loading this SDK into external Next Notes does not confer those capabilities. [SDK API contracts](https://appssdk.zoom.us/classes/ZoomSdk.ZoomSdk.html#getMeetingParticipants).

RTMS requires Developer Pack credits. Its General app needs chosen media scopes and event subscriptions; meeting users can be subject to host approval, and the meeting shows content access. This is a developer-managed optional integration, not an API-key instruction for the normal recording user. No RTMS start operation was performed. [RTMS overview](https://developers.zoom.us/docs/rtms/meetings/), [app scopes](https://developers.zoom.us/docs/rtms/meetings/add-features/), [host permissions](https://developers.zoom.us/docs/rtms/meetings/ux-overview/).

RTMS participant audio contains user ID/name and a server-creation timestamp; merged audio uses user ID zero. Transcript messages carry participant ID/name and speech intervals. Audio defaults to mono PCM at 16 kHz; startup buffering can extend to 60 seconds. Consequently, message arrival must not be used as capture time, and merged packets cannot support personal labels. Timestamp units and actual offset need observed packet tests. [Media schema](https://developers.zoom.us/docs/rtms/meetings/media/).

Inference: if Zoom authorization becomes available, start with transcript-only RTMS identity evidence, not a second PCM/ASR pipeline. The official quickstart permits transcript-only selection; implementation and its connection lifecycle still require a concrete authorized provider fixture. [REST quickstart](https://developers.zoom.us/docs/rtms/meetings/quickstart-rest-api/).

### Google Meet

An authorized meeting owner or participant can retrieve participant/session metadata. Anonymous and phone participants can have display names; signed-in participant identity does not guarantee email access. People/profile lookup has its own access limits. Joining or leaving a session supplies no speech association. [Participants guide](https://developers.google.com/workspace/meet/api/guides/participants).

Meet REST transcript entries contain the participant reference, text and start/end timestamps for their speech. Artifacts must be configured before the call ends; transcripts need not be accompanied by a recording. Authorized owners/participants can retrieve them, and REST entries are retained for 30 days. A missing artifact cannot reconstruct the past call. [Entry contract](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.transcripts.entries), [artifact access and retention](https://developers.google.com/workspace/meet/api/guides/artifacts).

The current Google calendar login requests calendar.readonly, not Meet metadata access. Meet REST uses a separate read grant; downloading Drive artifact files has different scopes. Prefer structured REST entries rather than asking for broad Drive access merely for attribution. [Authentication](https://developers.google.com/workspace/meet/api/guides/authenticate-authorize).

Google's current Media API get-started page, updated 2026-10-01, says preview signups are closed. It requires restricted media scopes plus meeting metadata access, compatible WebRTC behavior and client metrics. It lists `meetings.space.read`, whereas the REST auth page uses `meetings.space.readonly`; verify the method-specific scope before any implementation. Older indexed enrollment instructions are not evidence of current eligibility. [Current availability and requirements](https://developers.google.com/workspace/meet/media-api/guides/get-started).

Media API consent and meeting eligibility further limit coverage. Virtual streams can switch participants: RTP CSRC and participant/session metadata must establish identity, not tile order or stream slot. `MediaEntry` exposes audio CSRC, participant and session links. This is a possible future transport for an already eligible integration, not a small extension of the existing process tap. [Overview](https://developers.google.com/workspace/meet/media-api/guides/overview), [media entry schema](https://developers.google.com/workspace/meet/media-api/reference/dc/media_api.mediaentry).

## Small implementation slices through current seams

1. **Finish the name-save consumer repair.** Root first runs the exact original naming callback with the new unchanged actual-store cases, then the current production View method in the same signed build. Rejected metadata/context writes must preserve audio and retained data, expose a plain problem, and never claim full completion. This provides reliable manual labels immediately. Physical banner/click acceptance remains separate from callback proof.
2. **Obtain a real private provider sample.** After the coordinated build, run the existing one-shot diagnostic during one short Zoom call and one Meet call with known alternating speakers. Retain provider/app version, call/process/target identity, observation times, clipping/cost and accessible shape. Include a late join, duplicate name, deliberate overlap, a pinned non-speaker and a shared microphone. Repeated manual diagnostic invocations can characterize a timeline; do not turn them into production polling. A snapshot containing names alone passes roster observation and fails automatic-binding acceptance.
3. **Implement only the observed name producer.** First parse the retained real shape into transient suggestions in the existing naming sheet. Keep invite suggestions distinct from observed presence. Supply email only when an actual source supplies it. If useful participant details must survive restart, add backward-compatible optional fields to the existing Meeting record only after the real input establishes the need; do not introduce an identity ledger. An unchanged real fixture must fail before implementation and pass after; missing, duplicate, clipped and stale surfaces must refuse association without disrupting recording.
4. **Prove one provider-to-local utterance association.** If a Meet transcript already exists and an authorized grant is available, use structured entries from the exact conference instance as the first stronger producer fixture. Otherwise use actual diagnostic speaker evidence plus explicit user confirmation. Compare provider-attributed speech with local same-source speech and measured clock alignment. Require consistent unambiguous anchors; conflicting identity, overlap, changed clusters, room devices and unsupported clocks remain unknown. Derive timing tolerances from actual observations. Do not assign names by nearest roster position, calendar order, label number or a single visual tile.
5. **Commit through existing speakerNames/projection.** Preserve manually confirmed mappings. Verify transcript display, saved context, regenerated notes and restart all consume the supported mapping; owner/action payloads and confidence remain unchanged. Do not reuse names across meetings as inferred biometric identity. If automatic mappings need different authority/provenance from manual mappings, retain that narrowly on the existing Meeting record rather than treating every speakerNames entry as user-confirmed.
6. **Verify the actual call and performance.** Original/fixed actual provider fixtures must exercise the same production parser/admission/UI consumer, followed by a physical known-participant call. Record attribution accuracy and refused ambiguity, capture continuity, observer memory/time, UI responsiveness and denied-access behavior. Unknown names must remain usable and recording must continue immediately. Then repeat a long-call check without concurrent builds. No provider naming or instant/zero-cost claim before that evidence.

Other call applications continue to use local capture and the existing confirmation sheet. Add a provider adapter only when an actual accessible observation warrants it; none of the documented APIs grants universal access to every call's people or email.
