Read-only primary-source review. Next Notes records alongside the ordinary Zoom/Meet client; it does not host that client. ## Available routes and actual boundaries

| Route | What it can establish | Admission and limits for Next Notes |
| --- | --- | --- |
| Zoom Meeting SDK | Participants and per-user audio inside an SDK meeting client | Embeds a separate meeting experience in our app. It does not attach to stock Zoom. Current usage policy excludes bots/AI notetakers and directs that use to RTMS. Outside-account participation requires Zoom review and ZAK/OBF attribution since 2 March 2026. Not the proposed route. |
| Zoom Apps SDK | Display names, roster changes and active-speaker events inside an authorized Zoom App | Roster and all-speaker events require host/co-host and do not support Guest Mode. The self-speaker event is narrower. These JavaScript capabilities are not an external native-process API. |
| Zoom RTMS | Provider participant ID/name attached to speech transcripts or per-participant audio | Appropriate optional real-time provider route. Requires Developer Pack credits, a user-managed Marketplace app, meeting:read:meeting_transcript or meeting:read:meeting_audio grants and host-controlled access. Server clocks and buffered delivery require explicit local alignment. |
| Zoom past participants API | Name, join/leave information and possibly email for an authorized meeting occurrence | Paid Pro-or-higher account and appropriate resource access with meeting:read:list_past_participants (or its admin variant). No speaking intervals. A roster cannot name an acoustic cluster. |
| Meet REST | Authorized participant display names/session times; saved transcript entries with speaker participant and utterance interval | Owner/participant access and meetings.space.readonly or meetings.space.created scopes required for the participant/entry methods. Existing calendar.readonly is insufficient. Transcript must exist; entries are retained for 30 days. |
| Meet Media API | Its own WebRTC media source mapped to participant/session | Current preview accepts no new signups. Restricted meetings.conference.media.audio.readonly grant, eligible app/meeting and host/admin/participant controls apply. Not an available default for this recorder. |

## Evidence needed to bind a name

RTMS transcript packets carry participant ID/name and start/end timestamps; per-person audio carries the same identity, while merged audio uses ID zero. Its audio clocks originate at the server; startup delivery may contain buffered audio. These identify speech on that provider stream, not automatically our existing system tap. [RTMS media contract](https://developers.zoom.us/docs/rtms/meetings/media/).

Meet transcript entries reference a participant and speech start/end times. They can support post-call binding when an accessible artifact matches the actual conference. Google warns that entry text can differ from the generated document. Media API source mapping also applies to its own stream; stream slots can change. [Meet entries](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.transcripts.entries), [entry limitations](https://developers.google.com/workspace/meet/api/reference/rest/v2/conferenceRecords.transcripts.entries/list), [media source contract](https://developers.google.com/workspace/meet/media-api/guides/overview), [MediaEntry fields](https://developers.google.com/workspace/meet/media-api/reference/dc/media_api.mediaentry).

Implementation acceptance must match conference occurrence, audio source, provider/session identity and actual clock/quote evidence. Roster order, tile position, invite ordering, connected status and an isolated speaking badge cannot prove a diarization label. Duplicate names, rejoins, shared room microphones, overlap, clock uncertainty and ASR differences must remain unassigned when ambiguous. This is a design inference from the contracts above, not a verified physical binding.
