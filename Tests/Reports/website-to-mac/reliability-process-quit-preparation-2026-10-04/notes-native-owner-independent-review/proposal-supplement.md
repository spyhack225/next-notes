# Review of held Notes native owner proposal

Reviewed `notes-native-owner-design/manifest.json` SHA-256 `df070abedd3a643718673ca692a035eec6cb6c8b0a9ca88a5efb63007ffa0212`. Its three artifact hashes and nine finite source pins match at review time. This supplement leaves the earlier independent review and the held proposal unchanged. No compiler, native, model, owner-store or source change was made.

## Accepted source contract

The revised proposal correctly avoids a new Notes Task getter: one private service, one fixture UUID/`summarize` call, the actual count-one at Cocoa entry, synchronous `beginTermination()` snapshot and the existing App `for task in ownedNotesTasks { await task.value }` join identify the same operation. Its model path must use `configureTerminationNativeFixture` before `countTokens`/load; `ModelSpec.url` alone does not change `fileURL`. The nonnil injected provider in `NotesService.generate` avoids that method's nil-provider `unavailableReason` branch. `NotesGenerator.notes` begins with the supplied provider's `countTokens` and later generation, not a provider availability test.

The proposal's first/second vote discipline preserves `drained && ...`, mutual exclusion of diagnostic tuples, and one existing `nativeTerminationTask`. Pre-AppKit validation plus a narrowly scoped late INVALID path are needed because the current generic arm catch requests Cocoa quit after a setup error. An active decode hook schedules quit asynchronously: a prior success and entry event do not alone prove overlap at Cocoa. The actual first `.terminateLater` observer must still see one open bracket and the sole Notes task, or classify the input INVALID.

## Corrections before a patch

1. **Do not await the captured Notes array again in `safetyDrain`.** `NextNotesApp.applicationShouldTerminate` already awaits every `ownedNotesTasks` handle before `runtime.finishTermination()` and before any final vote. A second `.value` await on that same array adds no identity or return proof. The first-vote assertions can inspect task-map/native/store state after the existing join; the one-shot continuation can recheck that state and request the existing retry. It needs no array parameter solely for a repeat join. If the serial owner finds a distinct reason to pass the array, state the extra observable fact; do not describe a second await as the ownership proof.
2. **An optional read-only vote observer is justified for false drains.** The current `allowExit = drained && ...` short-circuits every diagnostic `finalReply` when `drained` is false. A nil-default Notes tuple callback receiving the already computed `(realDrained, actualAllowExit)` immediately before `sender.reply` can record the real false-drain vote without changing it, awaiting, writing a store, or starting a second quit. Otherwise a missing final callback cannot distinguish false runtime drain from absent measurement. Keep any deliberate first veto separate from this producer value; a false drain must not be reported as a successful forced-veto control.
3. **Public-copy-only admission still has an owner-model metadata read to resolve.** `NotesService.notesBrief` calls `Settings.shared.notesRelatedContext`. `Settings` initialization unconditionally computes the diarization default from `MeetingDiarizer.isDownloaded`; in a Notes native mode that getter uses ordinary `modelsRoot`, checks required files and enumerates that directory. The existing Notes fixture also calls `LlamaBackend.shared.initialize()` before summarize, which reads `Settings.shared.llmMetalEnabled`, ensuring the Settings initializer runs. The proposal is correct that the injected Notes provider avoids `LlamaLLMProvider.unavailableReason`; that does not establish no owner model asset metadata access across setup. The serial owner must qualify or isolate this existing Settings/diarization seam before claiming that only copied public model inputs are read. No model asset was inspected for this review.

The proposed immutable admission value cannot by itself make a copied file immutable across the later native open. The proposal already states that the current runtime guard checks canonical path/size and external source identity remains separately qualified. Retain that limitation. No new store, Task owner, native hook, delay or sequential wait is warranted by this review.
