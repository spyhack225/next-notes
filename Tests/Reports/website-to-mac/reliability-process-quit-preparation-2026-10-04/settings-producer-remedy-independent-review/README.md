# Settings initializer model-probe remedy: independent source review

**Source-only proposal review; no Source edit, parse, compiler, native run, model/asset access or owner defaults read.** The eight audited files and hashes are in `source-pins.json`. This addresses the first incorrect decision: `Settings.init` eagerly evaluates `MeetingDiarizer.isDownloaded` even when a stored explicit diarization answer already exists.

## Producer and proposed change

`Settings.init` reads `diarizeChoice = defaults.object(forKey: Keys.meetingsDiarize) as? Bool`, then calls `Self.diarizationDefault(stored: diarizeChoice, modelsPresent: MeetingDiarizer.isDownloaded)`. Swift evaluates the `modelsPresent` argument before entering the pure helper, so both explicit `true` and `false` still invoke the filesystem-backed getter. In an ordinary Notes native mode, `NativeDiarizationQuitSelfTest.isRequested` is false; that getter uses ordinary `modelsRoot`, checks required files and may enumerate the model directory.

Replacing only that assignment with `meetingsDiarize = diarizeChoice ?? MeetingDiarizer.isDownloaded` is the smallest responsible-producer correction. The right operand of `??` is lazy. A valid stored `true`/`false` returns the same effective value without touching the getter. Missing or non-Bool input keeps `diarizeChoice == nil` and runs the same model probe, preserving the automatic default. `meetingsDiarizeChoice` remains the original optional answer; the existing `applyDiarizationDefaultIfUnchosen()` guard and pure `diarizationDefault` helper remain unchanged. No settings constructor escape, alternate store, global availability override or second model check is justified.

## Exact isolated bootstrap

`Settings` selects `SelfTestHarnessDefaults.suite` when `SelfTest.isRunning`. That existing per-process `UserDefaults` suite copies owner selection only for `SelfTest.allowsSavedModelSelection`; `--selftest-native-termination` is not in that allowlist. An admitted Notes fixture may seed the existing suite's `"meetingsDiarize" = false` **before the first `Settings.shared` access** and before `NSApplication.shared`/`AppDelegate()`. `Settings.Keys` is private, so a separate fixture cannot name that symbol; its literal key must be checked against the declared key and the first singleton read must confirm `meetingsDiarizeChoice == false` and `meetingsDiarize == false`. Calling `Settings.chooseDiarization(false)` to seed would initialize the singleton first and miss the boundary. The suite already has per-process removal at exit; this does not create a second preference domain.

Existing Notes setup calls `LlamaBackend.shared.initialize()`, which reads `Settings.shared.llmMetalEnabled`; `NotesService.notesBrief` also reads `Settings.shared.notesRelatedContext`. Either can be the first touch. Seeding must precede both. A first-use admission/observer should fail INVALID if an earlier unexpected access constructed `Settings.shared` before seeding; source order alone is not an installed proof.

## Red-first qualification and limits

A nil-default bounded scalar observer at the **same initializer right-hand side** can count whether the actual getter path was entered; it must not return an availability value or replace the getter. Paired original/fixed variants need the same observer and same admitted fixture values. Use fresh processes because `Settings.shared` is one singleton per process. Explicit false and true should produce old count one/new count zero with the same stored choices; nil should still produce count one in both, with effective value matching the real probe. The existing pure helper test is related behavior, not proof of the constructor. No count or typecheck result is asserted here.

There is a genuine execution constraint: an **actual original** Notes-mode run with explicit false still enters the ordinary `MeetingDiarizer.isDownloaded` getter and reads owner model-root metadata. Under a no-owner-model-read requirement, that original cannot be run as a supposedly isolated public-copy-only native fixture without additional approved isolation. A scalar callback alone does not remove that read, and stopping before it would cease to exercise the full original producer. The serial runtime owner must choose a qualified safe original input/path and report exactly what it read, or keep the paired native proof held. The fixed path's zero-entry assertion plus isolated suite can establish its narrower no-probe behavior only after actual compiled/installed testing. None was run here.

The proposed lazy expression targets this one eager getter. It does not establish that every other constructor/runtime path is free of owner files, nor does it finish the Notes active-native/Cocoa or full-process shutdown proof.
