## Can the sole-map guard delay a normal answer?

The FIXED proposal checks `running[taskID] == nil` before accepting compatibility, restored-permission and missing-input continuations. That refuses a still-held predecessor rather than overwriting its only mapped Task. A refused input/approval leaves the saved waiting row and visible review available, but a human might need a second press if the row becomes actionable before predecessor return. Such a delay would violate the normal conversational path, so the source-only packet cannot claim fluent continuation yet.

The inspected normal call sites narrow that risk. `execute` catches `missingArgument`, commits `.waitingForInput`, updates activity and returns with no further await before `releaseWorker` (`AgentTaskManager.swift:1510–1534, 1371–1382`). Its ACP compatibility catch similarly commits `.waitingForCompatibilityCLI`, updates activity and returns without another await (`1535–1552`). A later UI click on `AgentView`'s input card calls `respondInput` (`AgentView.swift:655–713`); the ordinary MainActor task should have completed its defer before that user event. Restored-permission callbacks are installed by `restorePendingInteractions`, which is invoked after the manager catches `.needsPermission` and returns or on a fresh reader (`Manager:1170–1183, 1553–1569`). `PermissionGate.restore` refuses to replace an already pending request and retains a restored card until its owner accepts a decision (`PermissionGate.swift:91–101, 185–210`). A **live** original approval instead resumes its existing suspended gate/worker; the revision's `running == nil` restored-decision guard is not that live gate path. Source ordering supports a likely fast ordinary path, but does not prove the UI never acts through a reentrant callback or a still-held predecessor.

The fixed proposal also guards `resumeVoiceObjective` only on process quit, so it does not add a sole-map wait to normal voice input continuation. A denied restored permission remains permitted during quit; an approved request is refused before a grant/queued write, and the card stays visible. `respondPermission` similarly refuses only the approved action during quit. These distinctions need focused regression, not assumption.

## Required paired controls before release

Run one identical COMMON/FIXED fixture that uses the real isolated Manager and primary temporary store/backend for a normal `filesystem.read` missing-path question: observe the actual old worker's return, click/call the production `respondInput` once through its exact request ID, and require one accepted successor and one temporary read with no second answer. Add restored-permission approval and denial controls through the real `PermissionGate.restore` callback, including a currently live original gate so the two paths cannot be confused. Run an ACP compatibility control with its actual handshake producer if the permitted isolated peer is available; otherwise mark that control unrun. The pending-quit cases separately require a real AppKit `.terminateLater` and an actual backing bracket held across it, as in the frozen README. A helper-only map assertion or manufactured same-ID overlap is not a qualifying RED.

Until those controls pass, the new early refusal is a plausible safety contract with a possible first-click cost. It has no compiled or native verdict and cannot be described as complete process-quit ownership. Normal Done/default-false foreground waits remain unchanged in the proposal; do not add a sequential await to make this guard pass.
