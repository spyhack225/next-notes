## Four observations and their current limits

| Question | Existing real seam | What can be established; what remains unknown |
|---|---|---|
| Process/worker alive | Manager commits attempt/current app PID before backend entry; `running` owns actual Task handles; `releaseWorker` checks captured/current row identity. | The owner PID identifies the app process, not an individual worker. `running` is currently `[String: Task<Void, Never>]`, keyed only by task ID. A queued successor can already occupy that slot before its next attempt is allocated. A handle's presence or `!isCancelled` alone cannot certify the current attempt is executing or healthy. Absence cannot certify process death or cessation of effects: cancellation is cooperative and removes the handle before the body necessarily exits. There is no task production PID probe. |
| Backend session alive | LocalBackend submit is awaited by the Manager handle. ACPBackend owns an ACPSession inside runSession; ACPSession owns its JSONRPCStdioClient/child Process. | LocalBackend.health returns `ready` and status reads shared Manager task status; neither measures this invocation. ACPSession's didInitialize/sessionID survive close; close clears client but not those historical fields. No externally supplied exact-attempt session-liveness observation exists. ACP callbacks check shared task ID/running, not admitted attempt ownership. Compatibility ProcessHolder cancellation/reaping is scoped to its invocation and is not a durable lease. |
| Tool call in flight | Executor's actual final fire closure calls toolStarted before backing and toolCompleted in defer. Captured context and primary predicates fence facts. | An accepted start without completion is possible-action evidence. It is not proof the backing is still active: completion admission can fail after the backing returned. An accepted toolCompleted `threw` fact does not by itself prove no external effect. Events contain attempt/tool detail but no durable per-call receipt ID; transient draft receiptID is stored on the task instead. Repeated/nested/unbound calls cannot be paired by tool name or timestamp into complete coverage. |
| Receipt already created | ActionReceiptStore has injected safe-temp storage, captured taskAttempt/taskLeaseOwner, and exact ID lookup. Manager validates fired binding before the same toolStarted/activity transaction appends receiptIDs. | Exact joined rows are positive effect evidence. Preparing/waiting receipts can exist before the fire join; receipt persistence and SQL are separate boundaries. Task receiptIDs accumulate across explicit successor attempts, so resolve each ID and match captured ownership. Missing ID/file/row is never verifiedNotStarted. The store retains only 500 receipts. `receipt(for:) -> nil` does not distinguish missing evidence from unreadable history; loadedSafely retains that distinction privately. Recoverable readable rows from a partly damaged file do not establish complete coverage. |

Two read-boundary traps matter for a later collector. `TaskStore.journal(taskID:)` uses the broad `withConnection/openLocked` path, with CREATE and a 2-second busy timeout; it is not the existing-only, fail-fast authority reader. A production observation needs a task/journal snapshot through the already bound existing-only read transaction, never the diagnostic creator path. Similarly a receipt observer needs explicit source-quality information from ActionReceiptStore's existing load result; an empty/missing lookup cannot become a negative effect fact. Neither change is necessary for the recommended first handle slice.

## Smallest useful producer slice

Owner scope if authorized: `AgentTaskManager.swift` and additions to the existing actual `TaskWorkerAttemptSelfTest.swift`. No TaskStore schema, receipt writer, executor, ACP session, UI, scheduling or conversational loop change is needed for the first slice.

1. Replace the existing running-map value with a small value holding the **same Task** plus optional captured typed-local attempt identity (task ID, positive attempt, owner and admitted start). Publish a queued handle with no admitted binding. Bind that same slot immediately after its existing SQL running admission succeeds and before backend entry; use the admitted producer values, never reconstruct the binding from a later row. A rejected start produces no positive observation. Preserve existing source/schedule/backend eligibility and no class-dependent grant.
2. Expose a read-only snapshot of that exact binding through Manager, or the existing background execution diagnostic seam. Treat it as `owned handle present`, not `healthy` or `lease alive`. A future caller compares it with the authoritative row identity it is observing. Missing, mismatched, unbound, cancelled, held and waiting rows supply unknown/excluded evidence, never gone/no-effect. Do not make the observer another execution grant or weaken existing primary effect checks.
3. Keep all cancellation/release paths on the same existing map. Clear only the matching captured entry when an old execution exits, preserving a queued successor. Record an optional positive lifecycle observation at the actual existing backend-entry/exit checkpoints using the existing log/diagnostic seam; no extra save, journal row, full-history read, actor hop, await or timer. Do not add a new shared logger or expose prompt/argument/result data.
4. Leave process/session/tool/receipt questions independently unknown until their real producer observations are joined. The snapshot is useful because it avoids mistaking an app PID or replacement slot for the current worker; it cannot prove an unresponsive Task is healthy. No stale verdict, task state change, retry, reconnect, effect, token or permission follows from it.

This is a proposed feature prerequisite, not a verified product bug fix. Current releaseWorker already protects its known successor case; do not claim a reproduced handle-clearing defect without an actual unchanged failure. The narrow implementation should not be expanded into a general worker layer or a new registry.
