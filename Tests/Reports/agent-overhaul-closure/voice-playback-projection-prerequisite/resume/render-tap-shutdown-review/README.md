The sampled original hang is a confirmed lock cycle. All826 sample ticks show main thread inside `AVSpeechBacking.finishIfDrained` → playbackEngine.stop → graph uninitialization → RealtimeMessenger lock. The tap service holds the messenger while the exact `VoicePlaybackReference.install` callback at line17 queries engine.outputNode and waits for the graph mutex. Root terminated the owned hung PID72714; this interrupted native flag is not a pass. The unchanged original producer is retained with the actual sample and hashes in `proposal-freeze.json`; inherited/intermittent classification does not close the discovered bug.

The smallest proposed Source change is only `Agent/Speech/VoicePlaybackReference.swift`, root owned. The tap keeps its existing PCM copy, host/arrival timestamp capture, epoch capture and dispatch. Move the SAME captured engine's `outputNode.outputPresentationLatency` query into the EXISTING serial reference lane after epoch admission. No engine graph query remains inside the tap callback. A second epoch check immediately after the potentially blocked query skips a reference invalidated during shutdown. Do not hold the epoch lock while querying the AV graph. No queue, cache, owner, timer, DSP path, static latency, sleep, await or model pass is added.

Shutdown ordering is compatible with the existing lane.sync: Apple finish/stop first returns from player.stop and playbackEngine.stop, then calls VoicePlaybackReference.stopped; Pocket/Kokoro follow the same order. Once the engine releases its graph lock, an off-tap utility query can finish without requiring the tap messenger to acquire that graph. stopped increments/unlocks epoch before synchronizing the existing lane, so an already-admitted feed either completes before the existing clear or is rejected by the second check. The lane never calls stopped itself. This repairs the observed tap→graph lock edge; it does not promise every unrelated AV driver wait is impossible.

The local26.2 SDK `AVAudioNode.h:174–196` defines presentation latency as downstream maximum in seconds and says it can change on engine reconfiguration and should be fetched as needed. The proposal retains fresh same-engine lookup rather than install-time/stale cached latency. Its lookup now occurs at utility feed time, after captured render/arrival times. That is not an atomic latency snapshot for the tap's route: reconfiguration between capture and lookup may change the value, and the existing global stopped epoch does not independently cover every route notification. This race already lacked an atomic contract; do not claim exact route-transition acoustic alignment. AEC's existing renderHostTime/tapArrivalHostTime remain unchanged, and any route-specific future repair needs actual evidence, not a static cache or extra foreground gate.
