Current reducer pauses only already-playing outputs and leaves island speaking. Therefore a confirmed pre-onset queued pause is not represented; a first playback receipt forwarded while paused overwrites paused to playing/speaking. ## Proposed smallest safe patch

Only VoiceContracts.swift production logic changes. Preserve exact current OutputID guards and event ordering. Confirmed provisional events pause any current nonpaused output, including queued-before-onset, and project existing proposal or listening. firstAudio sets heard; a paused output remains paused and projects proposal/listening, while a genuinely current unpaused positive event retains normal onset. A small nonplaying projection helper reads the existing pending approval, floor, paused output and response; it cannot restore speaking. Matched finished/interrupted and committed interruption use it after their existing cleanup. responseEnded preserves speaking only when it is already the current projection, the floor is free and the retained current output is playing/heard; pending proposal has precedence.

Do not generalize that into a universal playing/heard→speaking helper. inputDiscarded currently changes paused→playing using historical heard; the backends resume via player.play()/renderer.resume() without a new positive receipt or pause epoch. Thus approvalResolved or later responseEnded could incorrectly manufacture resumed speaking from that state. The proposed body leaves inputDiscarded and approvalResolved unchanged. A callback queued before pause but delivered AFTER resume is still unsafe/unproven; the paused-only guard closes only the WHILE-paused case. Truthful awaiting-resume requires actual post-resume provenance plus the matching RealtimeAudioSession legacy projection before it can land; no extra display flag/store/channel is proposed here.
