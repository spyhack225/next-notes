## The smallest ready producer slice

Recommend a bounded **P6-05a: persist actual typed-local activity timestamps in the existing accepted transaction**, before a stale consumer exists. `heartbeatAt` and `lastProgressAt` have no production assignment; only isolated store fixtures supply them. An actual new positive local attempt therefore reaches its backend with a nil heartbeat, and accepted toolStart/toolComplete facts do not change that. This is a concrete missing producer from §2.5, not a need for a new scheduler.

At actual typed-local queued-to-running admission, use the same producer-owned time as attemptStartedAt to set heartbeatAt and lastProgressAt in the already written row. At accepted bound toolStarted/toolCompleted record admission, update those two fields on the existing row in the **same** primary transaction as its factual event, under the existing task/attempt/owner/status predicate. The tool fact must retain its current Bool/throw behavior: rejected SQL admission cannot advance timestamps or run the backing; rejected completion cannot produce task success. The in-memory row must roll back on primary rejection just as existing Manager updates do. Accepted SQL plus export failure remains accepted. Do not make a second heartbeat save, append a redundant heartbeat event for every existing tool fact, add an await, change state/resumePolicy, or add any timer.

Use the existing Manager mutation seam rather than mutating fields after `persist` returns or writing directly to the mirror. A narrow optional explicit draft argument on the existing private update function, or a correspondingly narrow existing-journal admission helper that shares its rollback/transition transaction, suffices. Preserve the captured worker predicate and the current exact journal ordering. Stamp producer-owned activity time; an externally supplied old draft timestamp must not move a live heartbeat backward. Keep this choice explicit in the implementation/fixture rather than deriving liveness from Activity strings.

**Owned source seams if authorized:** only `AgentTaskManager.swift` worker-start and journalContext record/update hunks, plus the root-owned existing `TaskWorkerAttemptSelfTest.swift` fixture additions. `AgentTaskStore`, `TaskStore`, `TaskEventJournal` and their schema already carry these optional fields and accept the existing predicate; no new write API, table, ledger or TaskHeartbeat object is needed for this first slice. `TaskDurability` header is a separate comment correction owned by root.

The timestamps describe accepted activity, not health. They do not classify the actual work, make a PID a lease, prove a backend is alive, identify a receipt, or justify retry. Model-token or ACP beats are explicitly outside this child. There is no current bound model-token producer that could safely call a per-token save: conversational RealtimeAgent streaming does not carry this positive task context, and doing so would synchronously write full history/export for each token.

## Why the whole stale detector is not ready

P6-05 depends on P6-04a and requires four observations before declaring stale. Existing `TaskRecoveryInput` represents some of them, but Manager startup supplies only the row and now; the planner always holds interrupted work and never dispatches. It is deliberately not the full recovery table. Do not add a boolean stale-to-failed transition as a shortcut.

| Required observation | Actual call sites today | Bounded consequence |
|---|---|---|
| Correct runtime class/window | Manager.execute assigns localDeterministic to every typed local backend, independent of tool. Native shell.run is a task, browser tools and MCP/composio tools can also be executed through that backend. Tool namespace/source/executionMode are available in the single manifest, but a local backend does not mean a 30-second operation. | Keep that field's current ownership-recognition meaning. Do not use its 30-second stale window until actual runtime classification is separately verified at the responsible dispatch producer. |
| Process/worker alive | Positive local attempt owner is the app PID. Same PID being alive does not prove this particular Task is executing; old/missing owners are held. No production reaper/probe feeds TaskRecoveryLeaseObservation. | PID absence/EPERM remains an observation, not authority. Do not infer missing worker from nil heartbeat or add a process killer. |
| Backend session alive/checkpoint | ACPSession is a local actor inside ACPAgentBackend.runSession; it exposes sessionID/didInitialize, not an owned live-session observation keyed to a positive attempt. Subscription closures hop to shared Manager and check task ID/running only. ACP attempts remain unbound. | No ACP periodic beat or renewed-lease claim until its actual owner/context/session producer is fenced. Do not create a parallel session registry just for this audit. |
| Tool currently in flight | The current SQLite journal records admitted toolStarted/toolCompleted with captured attempt. Persistent rejection is visible; a completed backing can exist without a completion fact when its save failed. Unbound/nested/ACP tools remain explicit coverage gaps. | An unmatched toolStarted is possible effect evidence, not safe-retry permission. A missing fact cannot certify verifiedNotStarted or complete journal coverage. |
| Receipt already created | ActionOrchestrator saves actual shared action receipts with taskID. It does not write TaskDurability.receiptIDs; receipts have no captured task attempt field. A task can create a waiting receipt and a later approved successor receipt. | A receipt for taskID is conservative possible-action evidence, not a proven exact-attempt join. Never choose a single receipt by date/list position or treat a missing join as no effect. Actual attempt/receipt binding remains a separate prerequisite toward IM-16. |

WaitingForInput/WaitingForPermission/compatibility cards must never be stale merely because the preserved runtime metadata remains localDeterministic. Detection must first exclude person-waiting statuses, as well as terminal/held rows, even before a future classifier is introduced. A 40-day-old card is still a card. Legacy waitingOnPerson remains no-window. The event timestamp child above changes no state and adds no consumer, so it introduces no false timeout or new audio/compute owner.

A full stale detector may later produce a read-only/log-only observation through existing planner input, retaining unknown/alive/tool-in-flight/receipt ambiguity. It cannot currently truthfully provide all four real production observations or complete P6-05. No shared periodic tick is needed yet: only ACP/scheduled classes would earn it, and neither currently has the bound ownership/runtime contract. Avoid building a timer/queue simply because the roadmap has a future row.

The useful path toward IM-16 is: establish actual admitted activity timestamps now; independently verify classification and exact attempt/receipt evidence next; then implement observational stale input and prescribed acceptance; only afterward complete the broader planner/recovery/remote-host contracts. This does not promote phases or reorder parent dependencies.
