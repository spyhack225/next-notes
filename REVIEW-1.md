**Verdict: REJECT.** The normal refresh and partial-grant paths are substantially improved, but account isolation and cancellation still have uncovered failure paths. Fix findings 1–6 before accepting these backend contracts.

Reviewed `claude2/google-c` at `ddf30b7b7a04addb0491a0837bd4316ca6ef96c9`, against `c6d850c`, including prerequisite packaging commit `713cbe8c` and the four subject commits. This is static review of committed source and retained evidence: no build, model, self-test, install, GUI, owner-store access, or private OAuth JSON access. ## Findings

1. **HIGH — A Keychain read failure can select a different person's gws credentials.** `Sources/NextNotes/Calendar/Google/GoogleTokenStore.swift:73`, `Sources/NextNotes/Agent/GoogleWorkspaceCLI.swift:216`, `:470`, `:487`. Every unsuccessful `SecItemCopyMatching` becomes nil, including access/authentication failures, not just item-not-found. A raw legacy grant has no `googleAppSignInSelected` preference (the fixture explicitly establishes this at `GoogleConnectSelfTest.swift:907`). If that grant is temporarily unreadable, `appSignInInEffect()` is false and `run()` discovers the installed gws and runs without the app-token addition. A separate CLI login can therefore answer or perform a write under another account. Retaining selection only when deleting a readable grant does not close this path. Preserve routing independently when adopting legacy grants and distinguish unavailable credentials from absent credentials; an unreadable store must refuse execution. Add a denied-read fixture with a runnable alternate login. Not checked: actual Keychain prompts/lock behavior.

2. **HIGH — Cancellation after token delivery can still launch backing.** `Sources/NextNotes/Agent/GoogleWorkspaceCLI.swift:481`, `:496`, `:572`, `:598`, `:670`. The token actor checks cancellation after shared refresh, but the runner suspends across the actor call and does not check again at executable entry. Cancel the caller after the token actor has returned and before the runner resumes. `spawn()` enters `withTaskCancellationHandler` already cancelled: its cancellation handler sees a process that is not running and does nothing, then the operation calls `process.run()`. Cancellation during the same pre-launch window has the same race. The cancelled task can start a send/create command. The retained fixture cancels at the refresh request (`GoogleConnectSelfTest.swift:626`), which cannot catch this later window. The process box needs a remembered cancellation state and coordinated cancellation/launch admission, plus a fixture paused immediately before launch. This flaw is inherited in the spawn seam, but prevents the new cancellation guarantee.

3. **MEDIUM — An old refresh's invalid_grant can delete a newly connected grant.** `Sources/NextNotes/Calendar/Google/GoogleAccessTokens.swift:75`, `Sources/NextNotes/Calendar/Google/GoogleOAuthClient.swift:102`. Reconnect saves the new Keychain grant first, then awaits token-actor invalidation. An outstanding refresh for the previous grant can resume on that actor in between. Its generation still matches, so `GoogleTokenStore.clear()` deletes the new record and the following invalidation is too late. The same read/write separation exists between reading a refresh identity and starting its refresh. Make grant replacement and refresh invalidation coherent through the existing token seam, and condition revocation deletion on the exact grant being revoked. Test an old held invalid_grant response racing successful reconnect. Not checked: a native scheduling reproduction.

4. **MEDIUM — Concurrent Calendar 401s cancel each other's shared refresh.** `Sources/NextNotes/Calendar/Google/GoogleCalendarProvider.swift:211`, `:226`; `Sources/NextNotes/Calendar/Google/GoogleAccessTokens.swift:92`. Two Calendar requests use cached token A. Request one gets 401, invalidates and starts refresh B. Request two's delayed 401 for A then unconditionally invalidates, cancels B and starts C. The first request, and any Workspace caller sharing B, fail with cancellation even though the caller was not cancelled. More delayed 401s repeat this and spend one refresh per invalidation. Invalidate only the access token that actually received the 401; a stale rejection must join the replacement refresh. The tests cover five successful concurrent reads and one serial pair of 401s (`GoogleConnectSelfTest.swift:947`, `:964`), not concurrent rejection. Not checked: real endpoint timing, sustained retry volume.

5. **MEDIUM — The planner sees tools with known missing scopes while status is probing.** `Sources/NextNotes/Agent/AgentCapabilityManifest.swift:502`, `:520`, `:1011`, `:1013`; `Sources/NextNotes/Agent/AgentService.swift:127`. With a Docs-only grant, cached gaps correctly withhold Mail. A forced status refresh sets `isProbing`; live manifest inputs become `.checking` while still carrying those Mail gaps. Readiness then returns `.ready` for `.checking` without consulting the gaps. Mail enters `allowed`, `selected`, and the planner catalogue until the probe ends. Execution still rejects it, but the claimed planner exclusion is false. Apply known per-tool gaps before the optimistic unknown/checking state rule. Test the actual live-input probing state with a partial grant; the new tests force `.signedIn` inputs. This is an inherited readiness shortcut newly relevant to scope gaps.

6. **MEDIUM — Declining Calendar still causes Calendar API calls and an initial authorized result.** `Sources/NextNotes/Calendar/Google/GoogleCalendarProvider.swift:72`, `:76`, `:89`; `Sources/NextNotes/Calendar/CalendarService.swift:222`, `:237`; `Sources/NextNotes/Calendar/Google/GoogleConnection.swift:120`, `:149`. Authorize returns `.authorized` after every successful token exchange, even a Docs-only or explicitly empty grant. CalendarService consequently lists calendars. The new connection controller also enables Calendar and calls `refreshGoogleCalendars()`. Unlike `events()`, `calendars()` never checks granted scopes, so it refreshes a token and sends a calendarList request that Google must reject. Return authorizationState after sign-in and enforce the permission in the list consumer before network entry. Add a Docs-only/empty-grant Calendar consumer fixture that asserts zero Calendar requests. Google's [multiple-scope policy](https://developers.google.com/identity/protocols/oauth2/policies) requires disabling declined functionality and avoiding its failing API calls.

## Secrets, packaging, and storage

The complete base-to-branch diff, including committed logs and patches, contains no recognizable real Google client ID or GOCSPX secret. Its sole numeric client-ID-shaped string is the clearly synthetic test value at `GoogleConnectSelfTest.swift:77`. This is a pattern scan, not comparison against the forbidden private file.

`Makefile:153` copies the placeholder plist; `:175` injects into the staged bundle before signing. `install: app` at `:230` and `release: app` at `:273` use the same step. With absent JSON, ordinary app assembly leaves the source-copy placeholders, and `GoogleAppClient.swift:178` resolves them as not configured. Malformed JSON produces a generic failure without a traceback. Python reads values internally: process arguments, make output, and shell tracing expose the code and file paths, not the JSON values. No new `set -x`, credential echo, or direct credential logging was found. Consent's browser URL carries the client ID but no secret; the token request carries the secret in its POST body through the uncached ephemeral PrivateURLSession. The bundled self-test prints only shape/status checks; the retained native runs were unbundled and skipped those packaging checks.

The target protection at `Makefile:326` rejects the canonical source plist and symlink aliases, but is not a general “built bundle only” boundary: an overridden `GOOGLE_OAUTH_PLIST` may name another repository plist, and a hardlink to the source has a different resolved path. Normal app/install recipes do not take those paths. Restrict the destination if arbitrary overrides are part of the supported safety contract. `Resources/Info.plist:43` also contains an unnecessary second placeholder pair inside the URL-type dictionary; only the top-level keys at `:77` are used.

The injector does not inspect/chmod the private input or destination; it preserves the copied plist's ordinary permissions. A desktop client's bundled secret is extractable by recipients by design, so this is not refresh-token protection. I did not inspect private-file permissions, installed bundles, OS crash reports, or external telemetry; no reviewed code explicitly sends injected values to those outputs, but absence from every possible crash artifact is not established.

Refresh token and granted scopes share the existing generic-password Keychain account `refresh-token`, service `ai.pivotstudio.nextnotes.google`, using AfterFirstUnlock for newly added items. Access token, expiry and client/grant cache identity stay in memory. Only the route-selection boolean is newly persisted in defaults. Existing advanced client ID/secret defaults remain; the injected app client is not copied into them. No second credential store or manifest was introduced.

## Scopes, consent, and release implications

Whole-branch scope-URL search finds the production base URL in `GoogleAppClient.swift:18` and the independent expected-set fixture in `GoogleConnectSelfTest.swift:122`. Main and the stated base retain only `calendar.readonly` in `GoogleOAuthClient.swift:22`. There is one production nine-scope consent list. `required` is a mail/calendar status subset and the two legacy constants are compatibility checks, not another consent request. Both production sign-in callers use the nine-scope default.

Requesting several scopes together is supported, and Google's [installed-app documentation](https://developers.google.com/identity/protocols/oauth2/native-app) says incremental authorization is unsupported for installed clients. That does not remove Google's requirement to request only permissions needed for functionality the person knowingly chose. Sheets, Slides, Tasks, Contacts and Forms currently have no mapped planner tools (`GoogleAppClient.swift:92`), so their all-at-once request needs a real feature justification before public verification. Owner preference alone does not establish eligibility. [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies).

`gmail.modify` and full `drive` are restricted scopes. Public distribution normally needs reviewed consent-screen branding, accurate declared scopes, justified restricted access and appropriate privacy disclosures. A single consent request does not bypass review or prevent users unticking permissions. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

The annual security assessment is conditional on access to restricted data from or through a third-party server, including the ability to do so; it is not automatically required merely because a desktop app names a restricted scope. Cloud-model processing of mail/Drive data may trigger that condition. `GoogleAppClient.swift:10` overstates this as unconditional. Actual data flows, exceptions and Google's assessment decision remain unverified. [Restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification). External Testing grants with these scopes expire after seven days; that is another expected reconnect situation, not evidence the person deliberately revoked access. [Refresh-token expiration](https://developers.google.com/identity/protocols/oauth2#expiration).

Revocation code matches only HTTP 400 with a successfully decoded top-level JSON `error` exactly equal to `invalid_grant`. It ignores `error_description` for classification. Other 400 bodies, invalid_client, malformed JSON, 401s, 403s, 5xx and transport failures do not delete the grant. There is no automatic token-endpoint retry/backoff; failed shared tasks are cleared so later calls request again. Selected typed grants and readable revoked legacy grants retain the app route. All Workspace tool calls, profile reads and probes converge on `run()`; the exception is the existing Terminal installer/sign-in UI, which invokes gws directly.
